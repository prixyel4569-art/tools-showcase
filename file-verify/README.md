# file-verify — 文件完整性校验

**找出"大小对了但内容是零"的稀疏文件。**

## 它解决什么问题

断点续传 / 预分配写的文件，会出现一种很难发现的情况：**文件大小完全正确，但内容是零**。

典型成因是「先 `truncate(总长)` 再分段填充」——
文件系统直接分配了全长，实际数据只写了前面一段，后面全是**全零洞**。

```js
// 这类代码就会产生稀疏文件
const fd = await fsp.open(DEST, 'w+');
await fd.truncate(TOTAL);        // ← 长度立刻到位
// 然后只填了一部分块……
```

**只看文件大小会以为下载完成，实际拿到的是个稀疏文件。**
很多下载器（包括本包里的 `dailyuploads-fast`）就是这么写的，所以需要这个工具兜底。

## 四个检查

| 步骤 | 做什么 |
|---|---|
| **1. 空洞扫描** | 逐块读全文，标出全零区间（相邻块自动合并，不输出碎片） |
| **2. 类型识别** | 按魔术字节判断 RAR5 / RAR4 / ZIP / 7z / MP3(ID3)；RAR5 额外扫尾部 end-of-archive 块判断是否截断 |
| **3. 完整哈希** | MD5 / SHA1 / SHA256，流式读取，内存占用恒定 |
| **4. 分段哈希** | 大文件（>64MB）每 100MB 一段的 MD5，整文件哈希不符时用来二分缩小损坏范围 |

## 用法

```powershell
node file-verify.mjs "<文件路径>" [期望字节数] [期望MD5]
```

```powershell
# 只看是否有空洞 + 全部哈希
node file-verify.mjs "D:\下载\游戏.rar"

# 顺带比对大小
node file-verify.mjs "D:\下载\游戏.rar" 748195840

# 顺带比对 MD5
node file-verify.mjs "D:\下载\游戏.rar" 748195840 19311d0d115ac2b54769ed15002d1132
```

## 核心技术点

**为什么必须"读全文"而不能只看大小**
稀疏文件在文件系统层面就是"合法"的 —— `stat().size` 返回的是逻辑长度。
唯一可靠的判断是**真的把每个字节读出来**看是不是零。

**合并相邻全零块**
逐 64KB 块扫描，一个 200MB 的洞会产生 3200 条记录。
读到全零块后继续向后读，合并成一段，输出才可读。

**流式哈希**
`for await (const c of fs.createReadStream(F))` 逐块喂给哈希对象，
内存占用与文件大小无关。几个 GB 的文件也能跑。

**分段哈希用于二分定位**
整文件 MD5 不符时，看哪一段 MD5 不对，就能把损坏范围缩小到 100MB；
必要时对那一段再跑一次（改小 SEG）继续二分。

**关于网盘取链 URL 里的 `chk=<hex32>-<size>`**
某些网盘会在下载链接里带这个参数。**它是服务端内部的校验 token，不是文件 MD5** ——
同一文件多次取链它保持恒定，但与真实 MD5 并不相符。拿它当哈希比对会永远失败。

## 边界

- 空洞扫描是**顺序读全文件**，几 GB 的文件需要几分钟（这是必要的代价）
- RAR5 尾部扫描只找 `end-of-archive` 块特征，**不是完整解析**；权威校验请用 `7z t`
- 加密归档无法从头部判断内部结构，只能靠 7-Zip 带密码校验

## 依赖

零依赖。只用 `node:fs` / `node:crypto`。Node ≥ 18。
